01 · Pipeline

Проведи значення крізь систему

Натисни кнопку — блакитний packet пройде через кожен етап pipeline.

Downstream: output і completion рухаються від Publisher до Subscriber.
Upstream: subscription, demand і cancel рухаються у зворотному напрямку.
Показати цей pipeline у Swift 
URLSession.shared.dataTaskPublisher(for: request)
  .map(\.data)
  .decode(type: User.self, decoder: JSONDecoder())
  .receive(on: DispatchQueue.main)
  .sink(
    receiveCompletion: { completion in
      print("completion:", completion)
    },
    receiveValue: { user in
      self.user = user
    }
  )
  .store(in: &cancellables)
Читай зверху вниз як downstream-потік: Data → User → main queue → sink.
02 · AnyCancellable

Одна дія — два різні фінали

Найважливіша ідея: sink повертає токен, який потрібно втримати.

Правильний шлях
1. Викликаємо sinkSubscriber приєднується до publisher.
2. Отримуємо AnyCancellableЦе токен керування subscription.
3. store(in:)Токен зберігається у Set<AnyCancellable>.
4. Pipeline живийЗначення доходять до sink, поки власник існує.
VS
Небезпечний шлях
1. Викликаємо sinkSubscriber створено.
2. Токен нікуди не записалиНемає сильного посилання.
3. AnyCancellable deinitDeinit автоматично викликає cancel.
4. Pipeline мовчитьНе crash, не error — просто немає output.
Правило пам’яті: AnyCancellable — не «результат sink». Це lifetime-token для subscription.
Порівняти неправильний і правильний код
✕ Cancellable втрачено
func observe() {
  publisher
    .sink { value in
      print(value)
    }
  // token одразу deinit
}
✓ Subscription утримується
private var cancellables =
  Set<AnyCancellable>()

func observe() {
  publisher
    .sink { value in
      print(value)
    }
    .store(in: &cancellables)
}
Коли власник cancellables деініціалізується, його subscriptions теж завершуються.
03 · Operator playground

Обирай оператор за поведінкою

Перемикай сцени. Кожна показує не визначення, а те, що реально відбувається.

Що потрібно зробити?

debounce: пропускає лише останнє значення після тиші

300 ms тиші
h he hel hell hello
До sink доходить: “hello”
Показати debounce у коді 
$query
  .debounce(
    for: .milliseconds(300),
    scheduler: DispatchQueue.main
  )
  .removeDuplicates()
  .sink { query in
    search(query)
  }
  .store(in: &cancellables)
removeDuplicates() часто ставлять після debounce, щоб не повторювати однаковий пошук.

collect(3): складає значення у «кошик»

1 2 3
1 2 3
До sink доходить: [1, 2, 3]
Показати collect у коді 
[1, 2, 3, 4, 5, 6].publisher
  .collect(3)
  .sink { batch in
    print(batch)
    // [1, 2, 3]
    // [4, 5, 6]
  }
  .store(in: &cancellables)
Звичайний collect() без числа чекає completion і лише тоді надсилає весь масив.

switchToLatest: старий запит програє новому

Request A cancel
Request B sink ✓
Ментальна модель: новий inner publisher замінює попередній.
Показати switchToLatest у коді 
$query
  .debounce(
    for: .milliseconds(300),
    scheduler: DispatchQueue.main
  )
  .map { query in
    api.searchPublisher(query)
      .catch { _ in Just([]) }
  }
  .switchToLatest()
  .receive(on: DispatchQueue.main)
  .sink { results in
    self.results = results
  }
  .store(in: &cancellables)
Кожен map створює inner publisher. switchToLatest() залишає підписку лише на найновіший.

Де насправді виконується кожен етап?

1
$query надсилає новий текст Зміна UI-властивості зазвичай приходить із main thread.
main
2
debounce планує 300 мс очікування Main thread не блокується. Combine лише ставить відкладену delivery-задачу в scheduler.
main scheduler
3
map створює search publisher Це зазвичай дешева синхронна операція, тому окремий thread hop не потрібен.
main
4
URLSession виконує мережеву роботу Scheduler у debounce не визначає, де працює мережа. URLSession виконує її асинхронно.
system / background
5
switchToLatest пропускає лише актуальний запит Попередній inner publisher більше не впливає на downstream.
publisher context
6
receive(on: .main) переносить результат Лише тепер ми явно гарантуємо main thread перед зміною UI-стану.
main
Чому debounce на main — нормально? Він не «спить» 300 мс і не заморожує UI. Він лише планує delivery через main scheduler.
Коли main уже поганий вибір? Якщо після debounce виконується важкий синхронний parsing або CPU-робота. Тоді використовуй background queue.
Ключове правило Combine

Більшість operators не створюють нову queue самостійно

map, filter, handleEvents та багато інших operators синхронно обробляють значення в тому execution context, у якому попередній publisher викликав їхній receive. Контекст змінюється лише тоді, коли це робить сам publisher або явний scheduler-operator, наприклад receive(on:).

Upstream викликає receive(value)
→
map / filter синхронно виконує closure
→
Downstream отримує результат у тому ж context
Подивитися спрощену реалізацію operator 
func receive(_ input: Input) {
  let output = transform(input) // map closure
  downstream.receive(output)    // синхронна передача далі
}
Якщо receive(_:) викликано на main queue, то синхронний transform теж виконається на main. Щоб змінити контекст перед ним, постав receive(on: processingQueue).
Порівняти два варіанти scheduler
✓ Типовий UI search
$query
  .debounce(
    for: .milliseconds(300),
    scheduler: DispatchQueue.main
  )
  .map(api.searchPublisher)
  .switchToLatest()
  .receive(on: DispatchQueue.main)
  .sink { [weak self] results in
    self?.results = results
  }
Background для важкої sync-роботи
$query
  .debounce(
    for: .milliseconds(300),
    scheduler: searchQueue
  )
  .map { query in
    expensivePreparation(query)
    return api.searchPublisher(query)
  }
  .switchToLatest()
  .receive(on: DispatchQueue.main)
  .sink { [weak self] results in
    self?.results = results
  }
Scheduler у debounce керує таймером і delivery після паузи. Він не переносить автоматично всю мережеву роботу на цю queue.
Порівняти receive(on:) і subscribe(on:) 
publisher
  .subscribe(on: backgroundQueue) // upstream subscription work
  .map(expensiveTransform)
  .receive(on: DispatchQueue.main) // downstream delivery
  .sink { value in
    updateUI(value)
  }
  .store(in: &cancellables)
subscribe(on:) впливає на upstream-підписку. receive(on:) змінює scheduler для downstream-подій після цього місця.
04 · Debug path

Pipeline мовчить. Куди дивитися?

Пройди одну гілку дерева. Це швидше за перечитування документації.

Чи збережено результат sink?

Найімовірніша причина знайдена

AnyCancellable деініціалізується одразу після створення. Додай .store(in: &cancellables) і перевір lifetime власника.

Рухаємося далі

Перевір completion, timing Subject, thread hop та operators, які можуть фільтрувати output: filter, removeDuplicates, debounce.

Інструментувати «мовчазний» pipeline
Debug probe 
publisher
  .handleEvents(
    receiveSubscription: { _ in
      print("1. subscribed")
    },
    receiveOutput: { value in
      print("2. output:", value)
    },
    receiveCompletion: { completion in
      print("3. completion:", completion)
    },
    receiveCancel: {
      print("4. cancelled")
    }
  )
  .print("SearchPipeline")
  .sink(
    receiveCompletion: { print($0) },
    receiveValue: { print($0) }
  )
  .store(in: &cancellables)
Постав probe перед і після підозрілого operator. Так ти знайдеш точне місце, де значення зникає.
4-minute review

Чотири образи для пам’яті

Не перечитуй. Подивись на образ і сформулюй правило своїми словами.

ФлоуOutput послідовно передається downstream через operators до sink.
КлючAnyCancellable утримує subscription живою.
Таймерdebounce чекає тиші перед delivery.
Естафетаreceive(on:) передає downstream іншому scheduler.
Відновити базовий pipeline з пам’яті 
publisher
  .map { ... }
  .receive(on: DispatchQueue.main)
  .sink(
    receiveCompletion: { ... },
    receiveValue: { ... }
  )
  .store(in: &cancellables)
Закрий блок і спробуй написати цю структуру самостійно без підказки.
Interview drill

Відповідай уголос, потім відкривай

Кожна картка містить коротку відповідь і типовий follow-up.

Чим receive(on:) відрізняється від subscribe(on:)?

subscribe(on:) впливає на upstream subscription work. receive(on:) переносить downstream delivery після цього operator.

Чому pipeline може «мовчати» без error?

Subscription могла бути скасована через deinit AnyCancellable, Subject міг надіслати значення до підписки, або output відфільтровано operator-ом.

Коли обирати combineLatest, а коли zip?

combineLatest реагує на найновіші значення обох publishers. zip формує пари за порядком надходження.

Як прибрати race між пошуковими запитами?

Перетворити query у publisher запиту та використати switchToLatest, щоб новий запит скасовував попередній.

Де виникає retain cycle із sink?

Власник утримує cancellable, subscription утримує closure, а closure сильно захоплює власника. Типовий fix — [weak self].

Чому @Published інколи дивує під час читання властивості?

Publisher емісить у willSet. Усередині subscriber нове значення вже передано аргументом, але сама властивість може ще містити старе.
