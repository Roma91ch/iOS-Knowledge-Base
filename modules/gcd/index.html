Grand Central Dispatch

Queue work. Let the system schedule threads.

GCD — системна abstraction над thread management. Ти описуєш work items, queue semantics, QoS і synchronization points; libdispatch та OS керують worker threads і вирішують, де фактично виконувати роботу.

01 · Mental model

Queue ≠ thread

Work item / closure
→
DispatchQueue
→
libdispatch / GCD
→
system-managed threads
→
OS scheduler / CPU cores
Core idea: queue визначає ordering / concurrency semantics. За винятком main queue, GCD не гарантує конкретний thread для work item.
02 · Serial vs concurrent

Queue type визначає, чи можуть work items overlap

Serial queue

Один item за раз. Добре для ordering та confinement mutable state.

A ━━━━━ B ━━━━━ C ━━━━━

Concurrent queue

Кілька items можуть виконуватись concurrently. Completion order не гарантований.

A ━━━━━━━━━ B ━━━━━━━ C ━━━━━━━━━
let serial = DispatchQueue(label: "com.app.state")
let concurrent = DispatchQueue(
    label: "com.app.processing",
    attributes: .concurrent
)
03 · Main, global, custom

Main queue

Serial queue bound to the app’s main thread.

DispatchQueue.main.async {
    label.text = "Done"
}

Global queues

System-provided concurrent queues using the global thread pool.

DispatchQueue.global(qos: .userInitiated).async {
    compute()
}

Custom queues

Власний label, QoS, serial/concurrent behavior, autorelease frequency та target queue.

04 · sync vs async

Це про caller waiting, а не про queue type

syncasync
CallerЧекає completionПовертається одразу
QueueМоже бути serial або concurrentМоже бути serial або concurrent
ResultМожна повернути прямо з closureРезультат приходить пізніше
let value = queue.sync { calculateValue() }

queue.async {
    calculateAndStore()
}
Classic deadlock: DispatchQueue.main.sync з main thread. Caller блокує main thread, а main queue не може почати item, поки main thread зайнятий caller-ом.
05 · QoS

Priority intent, не reserved thread/core

.userInteractive

Immediate UI responsiveness.

.userInitiated

User очікує результат для продовження flow.

.utility / .background

Long-running або deferrable work.

QoS — scheduler hint про importance та latency expectations. Він не виділяє окремий thread або CPU core.

06 · DispatchGroup

Fan-out / fan-in completion tracking

let group = DispatchGroup()

queue.async(group: group) { loadA() }
queue.async(group: group) { loadB() }

group.notify(queue: .main) {
    renderFinishedState()
}

Group не задає concurrency semantics і не створює threads. Він лише відслідковує completion набору operations як одного unit.

07 · Barrier

Concurrent reads + exclusive writes

final class Store {
    private let queue = DispatchQueue(label: "store", attributes: .concurrent)
    private var values: [String: Int] = [:]

    func value(for key: String) -> Int? {
        queue.sync { values[key] }
    }

    func set(_ value: Int, for key: String) {
        queue.async(flags: .barrier) {
            self.values[key] = value
        }
    }
}
read A ━━━━━━━ read B ━━━━━━━ WRITE BARRIER ━━━━━ read C ━━━━━
Important: barrier semantics для такого pattern мають сенс на app-created custom concurrent queue. Не розраховуй на barrier як на global cross-queue lock.
08 · DispatchWorkItem

Encapsulated work + scheduling metadata + cancellation flag

let item = DispatchWorkItem {
    doExpensiveWork()
}

queue.async(execute: item)
item.cancel()

cancel() позначає work item як cancelled. Якщо closure вже виконується, GCD не перериває його примусово. Для дострокового stop потрібен cooperative design — наприклад власний cancellation token/state або дрібніші work units.

09 · DispatchSemaphore

Permit counter / concurrency limiter — але wait() блокує thread

let gate = DispatchSemaphore(value: 2)

for job in jobs {
    queue.async {
        gate.wait()
        defer { gate.signal() }
        useLimitedResource(job)
    }
}

Good fit

Legacy synchronous code, bounded access to a scarce resource, controlled parallelism.

Be careful

wait() occupies a worker thread. Не використовуй semaphore як default спосіб “зробити async API synchronous”, особливо поруч зі Swift Concurrency.

10 · DispatchSource

Low-level events without manual polling loops

let timer = DispatchSource.makeTimerSource(queue: queue)
timer.schedule(
    deadline: .now(),
    repeating: .seconds(1),
    leeway: .milliseconds(100)
)
timer.setEventHandler {
    pollMetrics()
}
timer.resume()

Dispatch sources координують timers, file-system events, signals, process events, memory pressure, file-descriptor read/write readiness та інші low-level system events.

11 · Delayed execution
DispatchQueue.main.asyncAfter(deadline: .now() + 0.4) {
    showHint()
}

asyncAfter означає “не раніше заданого deadline”. Це не real-time guarantee: queue load і scheduler можуть відкласти фактичний start.

12 · concurrentPerform

Найбільш явний GCD tool для CPU data parallelism

DispatchQueue.concurrentPerform(iterations: chunks.count) { index in
    process(chunks[index])
}

What it does

Independent iterations можуть load-balance-итись між available cores. Це parallel-for pattern для великої CPU-bound задачі.

Still system-controlled

Не існує контракту “N iterations = N threads = N cores”. Actual degree of parallelism залежить від system resources.

Important: concurrentPerform є synchronous з погляду caller-а: метод не повертається, доки всі iterations не завершені. Тому не запускай важку роботу таким способом на main thread.
13 · What .concurrent guarantees

Permission for overlap, not physical simultaneity

let queue = DispatchQueue(label: "work", attributes: .concurrent)
queue.async { heavyA() }
queue.async { heavyB() }
.concurrent означає, що queue може мати кілька work items in flight. GCD та OS scheduler вирішують, скільки worker threads використати і чи буде реальне одночасне execution на різних cores.
14 · Queue-specific data & assertions

Debugging execution assumptions

let key = DispatchSpecificKey()
let stateQueue = DispatchQueue(label: "state")
stateQueue.setSpecific(key: key, value: "state")

stateQueue.async {
    assert(DispatchQueue.getSpecific(key: key) == "state")
}

Queue-specific values і dispatch preconditions корисні для diagnostics, коли legacy code має строгі queue-affinity assumptions.

15 · Common failures

Deadlock

Synchronous dispatch на queue, progress якої залежить від blocked caller.

Thread explosion

Blocking багато concurrent workers змушує system компенсувати thread pressure і може різко погіршити performance.

Shared mutable state

Concurrent queue сама по собі не робить data safe. Потрібні confinement, barrier, lock, actor або інша synchronization strategy.

Priority inversion

High-QoS work може чекати resource, який утримує lower-priority work.

17 · GCD vs Swift Concurrency
GCDSwift Concurrency
Queue-centric modelTask + actor + executor model
Closures submitted to queuesAsync functions and structured tasks
DispatchGroup / callbacksasync let, TaskGroup, await
Serial queue / barrier often protects stateActors provide language-level isolation
Cancellation mostly manual/cooperativeStructured cancellation propagation
Explicit queue/QoS mechanicsRuntime owns more scheduling details
No hard core/thread guaranteeNo hard core/thread guarantee
Modern iOS rule of thumb: prefer Swift Concurrency for new asynchronous app logic. GCD remains essential for legacy UIKit code, lower-level synchronization, callback-based APIs and understanding how older production code controls execution.
Interview recap

Queue ≠ thread

Queue defines execution semantics; threads are system-managed.

sync ≠ serial

sync means caller waits. Serial/concurrent is queue behavior.

Concurrent ≠ guaranteed parallel

Multiple work items may overlap; physical simultaneous execution depends on runtime resources and OS scheduling.
