02 · Context

Модель відповідає лише з того, що бачить зараз

Контекст — це інструкції, поточний запит, історія діалогу й додаткові дані. RAG потрібен лише тоді, коли треба швидко знайти текстові знання у великому масиві.

RAG: пошук перед генерацією

1. ІндексаціяДокументи діляться на уривки; для них створюються embeddings і зберігаються метадані.
2. ЗапитЗапит теж перетворюється на вектор або проходить інший пошук.
3. RetrievalПовертаються кілька найрелевантніших уривків, а не вся база.
4. GenerationLLM отримує запит + уривки і складає відповідь, бажано з джерелами.

Коли RAG доречний

«Запитай документацію», корпоративна база знань, великі приватні колекції контенту.

текстові знаннясвіжі дані

Коли не RAG

Точні структуровані факти: залишок, замовлення, календар. Краще викликати API або SQL-запит.

source of truth

Ризик

RAG не гарантує правду: може знайти не той уривок або не знайти нічого. Потрібні citations, фільтри й evaluation.

05 · Recall

Перевір себе за дві хвилини

Сильна інтерв’ю-відповідь: назви межу системи, ключовий компроміс, поведінку при помилці та спосіб виміряти успіх.

Чим агент відрізняється від самої моделі?
Модель генерує й міркує. Агентна програма додає ціль, стан, цикл дій, інструменти, політику дозволів і перевірку результату.
Коли використати RAG, а коли звичайний API?
RAG — для пошуку релевантних уривків у великій текстовій базі. API або SQL — коли потрібні точні структуровані, актуальні дані.
Яка найважливіша UX-вимога до агентної фічі?
Користувач не повинен втрачати контроль: зрозумілий намір, підтвердження дій із наслідками, можливість перервати та чесна поведінка при невпевненості.
Що б ти прототипував першим для нової AI-фічі?
Найризикованіший user journey: реальний prompt і дані, latency, failure states, чи розуміє користувач результат, а також як виміряти task success.
