Clean Architecture for iOSSwift · MVVM · SwiftUI Model–View
The dependency rule

Architecture is about direction, not folders.

Clean Architecture keeps business rules independent from SwiftUI, UIKit, networking, persistence and vendor frameworks. MVVM or Model–View decides how the presentation layer is organized; Clean Architecture decides which layer may know about which other layer.

01 · Core idea

The dependency rule

Source-code dependencies should point toward the business policy. Framework details stay at the outside edge.

Presentationrenders state and translates user intent
→
Domainowns app-specific rules and abstractions
←
Dataimplements domain-owned ports using concrete technology
The important part: Presentation can depend on Domain. Data can depend on Domain. Domain should not import SwiftUI, UIKit, SwiftData, Core Data, URLSession clients, analytics SDKs, or concrete databases.
Dependency direction is not runtime data flow. At runtime the UI may call a use case, which calls a repository implementation, which calls the network. In source code, the repository implementation conforms to a protocol owned by the inner layer, so the compile-time dependency still points inward.
02 · Boundaries

What should live where?

Use layers because responsibilities differ, not because a template says every feature must contain the same number of files.

Domain

Pure business meaning. Ideally framework-light and easy to test without launching the app.

  • Entities and value types
  • Business invariants and policies
  • Use cases when they express real behavior
  • Repository/service protocols needed by business rules
  • Domain errors

Presentation

Turns domain results into UI state and turns gestures into application actions.

  • SwiftUI Views / UIKit controllers
  • ViewModels in MVVM
  • Screen state and presentation-only models
  • Navigation state
  • Formatting that is truly UI-specific

Data / Infrastructure

Technology details and translation between external representations and domain models.

  • API clients and DTOs
  • SwiftData/Core Data models
  • Cache and persistence stores
  • Repository implementations
  • Mappers, analytics, file system, keychain
Show a minimal Domain + Data boundary in Swift 
// DOMAIN
struct Product: Identifiable, Equatable, Sendable {
  let id: UUID
  let name: String
  let price: Decimal
}

protocol ProductRepository: Sendable {
  func products() async throws -> [Product]
}

struct LoadProducts: Sendable {
  let repository: any ProductRepository

  func callAsFunction() async throws -> [Product] {
    try await repository.products()
      .sorted { $0.name.localizedStandardCompare($1.name) == .orderedAscending }
  }
}

// DATA / INFRASTRUCTURE
struct ProductDTO: Decodable {
  let id: UUID
  let title: String
  let amount: Decimal
}

struct APIProductRepository: ProductRepository {
  let client: APIClient

  func products() async throws -> [Product] {
    let dtos: [ProductDTO] = try await client.get("/products")
    return dtos.map { Product(id: $0.id, name: $0.title, price: $0.amount) }
  }
}
03 · Project organization

Prefer feature-first, then layer inside the feature.

Large global folders named Views, ViewModels and Services become hard to navigate. Feature boundaries keep related code close while preserving dependency rules.

App/
├── Composition/
│   ├── AppContainer.swift
│   └── AppRoot.swift
├── Core/
│   ├── Networking/
│   ├── Persistence/
│   └── DesignSystem/
└── Features/
    └── Products/
        ├── Domain/
        │   ├── Product.swift
        │   ├── ProductRepository.swift
        │   └── LoadProducts.swift
        ├── Data/
        │   ├── ProductDTO.swift
        │   ├── ProductMapper.swift
        │   └── APIProductRepository.swift
        └── Presentation/
            ├── ProductListView.swift
            ├── ProductRow.swift
            └── ProductListViewModel.swift   // MVVM only
App / CompositionThe composition root creates concrete dependencies and wires protocols to implementations. It is allowed to know both inner abstractions and outer concrete types.
CoreCross-feature infrastructure or UI primitives with stable ownership. Avoid turning Core into a dumping ground for unrelated helpers.
Feature / DomainWhat the feature means and what operations it supports. Keep framework details out.
Feature / DataHow this feature obtains and persists data. DTOs and persistence models should not leak upward.
Feature / PresentationHow users see and manipulate the feature. MVVM and Model–View differ here; the Domain and Data layers do not need to change.
Folder structure is optional evidence, not architecture itself. A small app may use fewer folders and still obey Clean Architecture. A huge folder tree can still violate it if Domain imports concrete infrastructure.
04 · Presentation option A

Clean Architecture + MVVM

The ViewModel belongs to Presentation. It may call domain use cases, but it should not become a substitute for the Domain layer.

SwiftUI Viewrender state, send events
→
ViewModelscreen state + orchestration
→
Use Casedomain behavior
MVVM example with Observation 
import Observation
import SwiftUI

@MainActor
@Observable
final class ProductListViewModel {
  enum State: Equatable {
    case idle
    case loading
    case loaded([Product])
    case failed(String)
  }

  private let loadProducts: LoadProducts
  var state: State = .idle

  init(loadProducts: LoadProducts) {
    self.loadProducts = loadProducts
  }

  func load() async {
    state = .loading
    do {
      state = .loaded(try await loadProducts())
    } catch is CancellationError {
      // Cancellation is expected lifecycle behavior.
    } catch {
      state = .failed("Could not load products")
    }
  }
}

struct ProductListView: View {
  @State private var model: ProductListViewModel

  init(loadProducts: LoadProducts) {
    _model = State(initialValue: ProductListViewModel(loadProducts: loadProducts))
  }

  var body: some View {
    Group {
      switch model.state {
      case .idle, .loading:
        ProgressView()
      case .loaded(let products):
        List(products) { ProductRow(product: $0) }
      case .failed(let message):
        ContentUnavailableView("Error", systemImage: "exclamationmark.triangle", description: Text(message))
      }
    }
    .task { await model.load() }
  }
}

Good ViewModel responsibility

Own screen-level observable state, coordinate user events, call use cases, translate domain outcomes into presentation state.

ViewModel smell

Building SQL predicates, decoding JSON, implementing pricing rules, doing cache invalidation, or becoming a 1,500-line “everything object.” Those belong elsewhere.

05 · Presentation option B

Clean Architecture + SwiftUI Model–View

SwiftUI does not require a ViewModel for every screen. A View can own presentation state and call a domain use case directly without violating Clean Architecture.

SwiftUI Viewrender + local screen state + task lifecycle
→
Use Casedomain behavior
→
Repositorydomain contract, data implementation
Model–View example without a ViewModel 
import SwiftUI

struct ProductListView: View {
  enum State: Equatable {
    case idle
    case loading
    case loaded([Product])
    case failed(String)
  }

  let loadProducts: LoadProducts
  @State private var state: State = .idle

  var body: some View {
    Group {
      switch state {
      case .idle, .loading:
        ProgressView()
      case .loaded(let products):
        List(products) { ProductRow(product: $0) }
      case .failed(let message):
        ContentUnavailableView("Error", systemImage: "exclamationmark.triangle", description: Text(message))
      }
    }
    .task { await load() }
  }

  private func load() async {
    state = .loading
    do {
      state = .loaded(try await loadProducts())
    } catch is CancellationError {
      // The View disappeared or the task was replaced.
    } catch {
      state = .failed("Could not load products")
    }
  }
}
Here “Model–View” means SwiftUI’s view-centric design: the View owns UI state and lifecycle orchestration, while business rules still live in Domain types/use cases and data access still lives behind repository boundaries. “No ViewModel” must not become “put all business logic in the View.”

Model–View fits well when…

The screen has straightforward state, SwiftUI already gives the lifecycle you need, and most important behavior is cleanly modeled in Domain services/use cases.

Add a state model when…

State transitions become complex, several sibling views need the same screen state, orchestration is substantial, or isolating presentation behavior materially improves tests and readability.

06 · Choosing presentation style

MVVM vs Model–View is not an architecture war.

Both can respect the same Domain/Data boundaries. Choose the amount of presentation abstraction that makes the feature easier to change and reason about.

ConcernMVVMSwiftUI Model–View
Screen stateUsually owned by @Observable ViewModelUsually @State / bindings in the View or a focused state object
User eventsView forwards to ViewModel methodsView handles presentation event then calls a use case/service
Business rulesDomain in both designs — not the ViewModel and not the View
Data accessRepository abstraction + Data implementation in both designs
Best fitComplex orchestration, shared screen state, presentation state-machine testingNative SwiftUI lifecycle, simple-to-medium screens, less indirection
Main riskMassive ViewModels that absorb Domain/Data responsibilitiesMassive Views with hidden business logic and tangled side effects
07 · Migration

Move between MVVM and MV without touching the inner layers.

If Clean Architecture boundaries are healthy, changing presentation pattern should mostly be a Presentation-layer refactor.

MVVM → Model–View

1
Freeze Domain and DataDo not move use cases or repositories into the View just because the ViewModel is going away.
2
Classify ViewModel codeBusiness rules → Domain. DTO/network/persistence → Data. Pure screen state/orchestration → Presentation.
3
Move simple screen state into the ViewUse @State, bindings, .task(id:), onChange and small presentation helpers.
4
Inject use cases/servicesThe View calls stable Domain-facing interfaces; concrete implementations are still assembled at the composition root.
5
Delete the ViewModel only if it no longer adds valueIf a substantial state machine remains, keeping a focused @Observable model may still be the cleaner design.

Model–View → MVVM

1
Identify presentation complexityLook for many related @State properties, repeated event orchestration, sibling coordination, or difficult state-transition tests.
2
Extract one screen state ownerCreate an @MainActor @Observable ViewModel with UI state and intent methods.
3
Move only presentation behaviorFormatting/state transitions can move. Business rules stay in Domain; persistence/networking stay in Data.
4
Keep the View declarativeThe View renders ViewModel state and forwards events without knowing implementation details.
5
Preserve dependency injectionThe ViewModel receives use cases/protocols, not singleton networking clients or concrete databases.
Migration heuristic: classify code before moving it 
// If this code answers...                         Put it in...
// ------------------------------------------------------------
// "What is valid in our business?"                 Domain
// "What operation does this feature perform?"      Domain / Use Case
// "How do we fetch/store it?"                      Data / Infrastructure
// "What should this screen show right now?"        Presentation
// "How does a tap change screen state?"            Presentation
// "Which concrete implementation do we construct?" App / Composition
08 · Testing

Test at the boundary that owns the behavior.

Clean Architecture is useful when tests become simpler and more targeted — not when every type gets a mock just because it can.

Domain tests

Business rules, use cases, ordering, validation, pricing, eligibility and error semantics. Usually fast and framework-free.

Data tests

DTO mapping, repository behavior, cache/network policies, persistence translation and integration with concrete infrastructure.

Presentation tests

State transitions when complexity warrants them. In MVVM test the ViewModel; in Model–View prefer domain tests plus focused UI/snapshot tests rather than recreating SwiftUI in unit tests.

Use-case test without UI or networking 
struct ProductRepositoryStub: ProductRepository {
  let result: Result<[Product], Error>
  func products() async throws -> [Product] { try result.get() }
}

@Test
func productsAreSortedByName() async throws {
  let repository = ProductRepositoryStub(result: .success([
    Product(id: UUID(), name: "Zest", price: 3),
    Product(id: UUID(), name: "Apple", price: 2)
  ]))

  let products = try await LoadProducts(repository: repository)()

  #expect(products.map(\.name) == ["Apple", "Zest"])
}
09 · Failure modes

Common “Clean Architecture” mistakes

The goal is independent change, not ceremony. These smells often create more coupling while looking architecturally sophisticated.

Domain imports infrastructure frameworks

If a Domain entity is a SwiftData @Model, NSManagedObject, API DTO or SwiftUI ObservableObject, the inner layer now depends on an outer detail.

Use case for every trivial getter

Use cases should encode meaningful application behavior or a useful boundary. Wrapping every repository call in a one-line type can add ceremony without clarity.

Protocol for every concrete type

Abstract at architectural seams and where substitution matters. “Protocol-oriented” does not mean an interface for every helper.

ViewModel as a dumping ground

A ViewModel that owns networking, persistence, caching, analytics, business rules and navigation is not clean just because the View is small.

DTOs leak into Presentation

External API shape should not define UI or business semantics. Map it at the Data boundary.

Global service locator everywhere

A giant environment/container accessed from every layer hides dependencies. Prefer explicit feature-level dependencies and keep composition at the edge.

@MainActor on everything

Presentation state commonly belongs on MainActor. Network/data/domain work should not be globally main-actor isolated just to silence concurrency warnings.

Folder purity over feature cohesion

One global Views folder and one global ViewModels folder may satisfy a diagram while making ownership and feature changes harder.

10 · Practical checklist

How to apply it correctly

A lightweight review list for a new feature or architecture refactor.

✓Can Domain compile conceptually without SwiftUI/UIKit, networking and persistence details?
✓Are repository/service abstractions owned by the layer that needs them, with concrete implementations on the outside?
✓Are DTOs and persistence models translated before crossing into Domain/Presentation?
✓Does the composition root decide concrete implementations instead of feature code constructing them ad hoc?
✓Does MVVM contain presentation orchestration rather than business/data logic?
✓If using Model–View, is the View still thin enough that business rules remain outside SwiftUI?
✓Can the presentation pattern change without rewriting repositories and business rules?
✓Are boundaries buying testability, replaceability or clarity — rather than existing only for symmetry?

Interview mode

Senior-level questions

Open each card only after answering aloud.

What is the most important rule in Clean Architecture?

The dependency rule: source dependencies point toward policy. UI and infrastructure can depend on domain abstractions, but the Domain should not depend on concrete UI, network, database or vendor-framework details.

Where should repository protocols live?

Usually with the inner layer that consumes the abstraction — commonly Domain/Application. The Data layer then implements that protocol. This is dependency inversion: the policy defines what it needs; infrastructure adapts to it.

Can a SwiftUI app use Clean Architecture without ViewModels?

Yes. Clean Architecture and MVVM solve different problems. A SwiftUI View can own local presentation state and call a domain use case directly. The design stays clean as long as business rules and data-access details remain behind appropriate boundaries.

When would you prefer MVVM over a Model–View approach?

When screen orchestration/state transitions are substantial, multiple child views share the same screen state, presentation behavior needs focused unit tests, or a dedicated state owner materially improves readability. I would not add a ViewModel automatically to every SwiftUI screen.

What are signs of over-engineered Clean Architecture?

One-line use cases for every getter, protocols for every type, duplicated models with no boundary benefit, enormous DI containers, and layers that only forward calls. Each abstraction should buy independent change, testability, ownership clarity or a meaningful policy boundary.

How would you migrate an MVVM feature to SwiftUI Model–View?

First classify the ViewModel code. Keep business rules in Domain and data work in Data. Move only simple screen state and lifecycle orchestration into the View, continue injecting the same use cases, and retain a separate state model if the remaining presentation complexity still justifies it.

How does Clean Architecture help with replacing Core Data with SwiftData or changing an API client?

If persistence and networking are outer implementations behind stable domain-facing contracts, replacement should mostly affect the Data/Infrastructure layer and composition root. Domain and most Presentation code should remain unchanged.

Is a folder named Domain enough to make the code clean?

No. Architecture is defined by responsibilities and dependency direction, not names. If files inside Domain import SwiftUI, concrete persistence types, API DTOs or infrastructure implementations, the boundary is already broken.
