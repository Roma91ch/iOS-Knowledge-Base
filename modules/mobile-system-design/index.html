01 · Boundaries

Спочатку розділи read path і write path

Це прибирає більшість плутанини. Search і hotel details можуть бути tolerant до stale data. Booking — ні.

Read path

1
Search / hotel dataМожна кешувати, показувати stale-while-refresh, prefetch.
2
AvailabilityКеш корисний для UX, але не є фінальною гарантією.
3
Images / metadataДобрий кандидат для агресивного cache + CDN.

Write path

1
Create reservationЛише сервер може підтвердити, що room ще доступний.
2
Payment / holdПовторний tap або retry не повинен створити другу операцію.
3
Cancel / modifyПотрібен authoritative server response і конфліктна стратегія.
Memory rule: cache може прискорити рішення користувача, але не може сам гарантувати бізнес-інваріант.
02 · Read path

Швидкий UI через local-first читання

Користувач не має дивитися на spinner щоразу, коли повертається на hotel details.

→

→

T+networkRefreshFetch latest price / availability.
T+updateReconcileUpdate local cache and visible state.
Показати client-side repository sketch
actor HotelRepository {
    private let api: HotelAPI
    private let cache: HotelCache

    func hotel(id: Hotel.ID) async throws -> Hotel {
        if let cached = await cache.hotel(id: id) {
            Task { try? await refresh(id: id) }
            return cached
        }
        return try await refresh(id: id)
    }

    @discardableResult
    private func refresh(id: Hotel.ID) async throws -> Hotel {
        let hotel = try await api.hotel(id: id)
        await cache.save(hotel)
        return hotel
    }
}
Trade-off: для availability додай timestamp / freshness indicator. Не маскуй старі дані як гарантовано актуальні.
03 · Booking write path

Один намір користувача → один idempotency key

Ключ створюється перед першим booking request і повторно використовується для retry цього самого наміру.

Tap Bookстворити key
→
POST /reservationsIdempotency-Key header
→
Serveratomic availability check + create

Network timeout після POST

1
Не знаємо результатRequest міг дійти до сервера.
2
Retry з тим самим keyServer повертає той самий booking result замість дубля.
3
Persist pending intentЯкщо app kill — можна безпечно завершити reconciliation.

Що не робити

×
Новий key на кожен retryЦе перетворює retry на нову бізнес-операцію.
×
Вірити cached availabilityМіж screen render і tap room уже могли забронювати.
×
Blind optimistic successBooking success має бути підтверджений backend.
Показати booking request sketch
struct BookingIntent: Codable {
    let key: UUID
    let hotelID: String
    let roomID: String
    let dates: DateInterval
}

func submit(_ intent: BookingIntent) async throws -> Reservation {
    try await api.createReservation(
        intent,
        idempotencyKey: intent.key.uuidString
    )
}
Important distinction: idempotency key захищає від повторної обробки одного наміру. Він не «лочить» кімнату сам по собі — availability / inventory consistency вирішується сервером.
04 · Offline & reconciliation

Не всі actions однаково офлайнові

Read UX може бути local-first. Booking — pending, але не confirmed, доки немає server acknowledgement.

OfflineBrowse cacheHotel details і recent search можуть працювати.
BookCreate pending intentПояснити, що confirmation ще немає.
OnlineSubmit safelyТой самий idempotency key.
ConflictResolve explicitlyRoom unavailable → show alternatives, not silent overwrite.
State machine: idle → submitting → confirmed | failed | needsReconciliation. Це краще за кілька незалежних Boolean flags.
05 · Reliability

Логуй intent, а не лише HTTP status

При booking bugs важливо відновити історію одного користувацького наміру через retries і app lifecycle.

Відновити booking state machine з пам’яті
enum BookingState {
    case idle
    case submitting(intent: BookingIntent)
    case confirmed(Reservation)
    case failed(Error)
    case needsReconciliation(BookingIntent)
}
Interview drill

Відповідай уголос, потім відкривай

Тримай відповідь короткою: рішення → причина → trade-off.

Де має жити source of truth для availability?

Фінальний source of truth — backend/inventory system. Client cache може пришвидшувати display, але перед booking server має атомарно перевірити актуальну availability.

Що робити, якщо create booking timeout-нув після відправки?

Вважати результат unknown, не failed. Retry з тим самим idempotency key або виконати status reconciliation. Новий key може створити дубль.

Коли створюється idempotency key?

Коли формується один конкретний booking intent, до першого POST. Усі retries цього intent повторно використовують той самий key. Новий intent користувача отримує новий key.

Чи варто робити booking optimistic UI?

Можна optimistic показати submitting/pending, але не confirmed. Confirmation — лише після server acknowledgement, бо inventory може конфліктувати.

Як би ти підтримав app relaunch під час booking?

Persist pending BookingIntent разом із idempotency key. Після launch перевірити server status або безпечно retryнути, потім перейти у confirmed/failed/reconciliation state.

Який mobile-specific trade-off найважливіший тут?

Баланс між швидким local-first UX і серверною коректністю. Mobile має нестабільну мережу та lifecycle interruptions, тому cache/retry/reconciliation — частина дизайну, не edge case.
